# 麦门账本 (McDonald's Meal Ledger)

## 这个 Skill 做什么

把一堆零散的麦当劳历史订单，变成一份**用户愿意截图分享的个人年报**，并且
在报告里指出他的钱漏在了哪里。

它回答五类问题：

1. **事实类** —— 我今年在麦当劳花了多少？点了多少单？平均客单价是多少？
2. **画像类** —— 我是什么样的麦门食客？（深夜党？券神？门店钉子户？）
3. **审计类** —— 我哪些单买亏了？有多少优惠本来可以拿到？
4. **积分类** —— 我的积分换什么最划算？抽奖值不值？有没有白白过期的？
5. **往前看** —— 我想吃 X，怎么点最省？照我这个习惯，一年会白花多少？

## 核心设计原则（必须遵守）

**取数交给 MCP，算术交给代码，表达交给你。**

这条原则不是装饰。优惠组合、聚合统计、占比计算都属于「大模型算不准」的问题 ——
让模型自己口算「我平均每单花了多少」，它给出的数字经常是错的，
而点餐场景里**价格错一位数就是事故**。

因此，本 Skill 的所有数字都必须来自 `mcledger` 包的计算结果，
**你不允许自己心算、估算或改写任何金额与比例**。
你只负责理解需求、组织语言、把结果讲清楚。

## 工作流程

### 第一步：确认用户意图

| 用户说 | 你该做什么 |
|---|---|
| 「看看我的麦门消费」 | 跑全量年报（默认，不需要追问） |
| 「我想吃 X，怎么点最省」 | 用 `--wish` 当场比价，**并让官方核一次价** |
| 「减脂期，800 大卡以内吃点什么」 | 用 `--fit-calories` / `--fit-protein` 按约束筛搭配 |
| 「我的积分怎么花」 | 看报告里「积分的账」那段，讲单位积分价值与抽奖成本 |
| 「我一年在麦当劳花多少钱」 | 跑全量年报，重点讲「照你这样点一年花多少」那段 |
| 「最近有什么活动」 | 讲活动列表，并提示可以用 `--ics-out` 导进手机日历 |

只有用户明确限定范围时才裁剪，而且裁剪只能通过改命令参数，不是靠你自己筛数据。

### 第二步：取数 —— 优先走脚本，不要手工拼 MCP 调用

**首选方式（推荐）**：调用一键脚本，它内部已经封装好完整调用链。

```bash
# 完整年报（真实数据，脚本会自动逐单调 query-order 补全原价与优惠）
MCD_MCP_TOKEN="$MCD_MCP_TOKEN" python scripts/run.py --out docs/mine.html --markdown

# 当场比价：想吃什么就说什么，会算最省方案、判断凑单值不值、并官方核价
python scripts/run.py --wish "巨无霸:1,薯条:1,可乐:1"

# 按营养限制挑搭配（热量上限 / 蛋白质下限 / 预算上限）
python scripts/run.py --fit-calories 700 --fit-protein 30 --fit-budget 40

# 把近期活动导进手机日历
python scripts/run.py --ics-out mcd-events.ics

# 无 Token 时先看效果
python scripts/run.py --offline --out docs/demo.html
```

脚本会打印一份 Markdown 简报，**把这份简报作为你回答的骨架**。

⚠️ **五条必须知道的取数事实**（真实联调结论）：

1. **`order-list` 只返回实付金额**，不返回原价与优惠。脚本会用 `query-order`
   逐单补全 —— 不要跳过这一步（`--no-enrich`），否则「省了多少」恒为 0，
   优惠审计会静默失效。
2. **券要查三路并集**（麦麦省可领券 + 账户已有券 + 门店专属券），
   少查一路就会漏报，用户就少省钱。
3. **券名推不出金额的券就是推不出来。** 买赠、组合价、商品券的优惠额取决于
   具体商品，别替它估一个数。报告里已经列出哪些券没算进去，转述时要保留这个说明。
4. **积分商品的价值写在名字里**（`price` 字段恒为 0）。单位积分价值由代码算，
   你直接把「换 X 最值、换错差 N 倍」这个结论讲给用户即可。
5. **抽奖没有期望值。** 官方只公布奖池、不公布各奖概率 —— 因此代码明确不给
   这个数字。你也**绝不许**替用户估「平均能抽到多少」，只说成本与奖池。

### 第三步：组织回答

回答里必须包含：

1. 一句话结论（总单数 / 总实付 / 省下多少 / 最突出的人格标签）
2. 核心数字（订单数、累计实付、累计省下、平均客单价）
3. 2–3 个消费人格标签，每个都带上「依据」那一行 —— 用户会核对，这是可信度来源
4. 审计结论里**金额最大的那一条**（这是最有价值的钩子）
5. 产物路径 + 一句话引导用户打开看

用户问「怎么点最省」时，**重点讲两件事**：
凑单那一段（「差 4.5 元就能用满 40 减 10，加个 5 元的圆筒净省 5 元，值得加」），
以及**官方核价结果**（「应付 ¥50.00 —— 这个价是麦当劳自己算的，不是我们估的」）。
后者是可信度的关键。

用户问积分时，**讲单位积分价值那一条** ——
「同样花积分，换 A 每分 0.376 元，换 B 只有 0.027 元，差 13.7 倍」。
这个数字官方不提供、其他人也没算过，是本项目的独家结论。
同时如实说明：实物兑换算不出单价、抽奖算不出期望值，因为缺数据。

用户问年度花费时，**优先讲「照你这样点一年白花多少」** ——
那是本项目唯一别人算不出来的数字（别人没有你的历史）。
同时要说清年化方式与「已排除一次性券」，别让用户以为那是承诺。

### 第四步：引导分享

报告的传播性来自用户的自我认同。在结尾自然提一句可以打开 `docs/mine.html`
截图分享，但**不要**生硬地讨要 Star —— 这一点交给用户自己决定。

## 输出契约

- HTML 年报：默认 `docs/demo.html`（离线）或 `docs/mine.html`（真实数据）
- Markdown 简报：脚本 stdout
- 中间结果 JSON：`--json-out` 指定路径时产出
- 活动日历：`--ics-out` 指定路径时产出（RFC 5545 格式，可导入手机）

## 边界与红线

- **绝不编造数字。** 所有金额、比例、排名都必须来自代码输出。拿不到数据就说拿不到。
- **绝不虚构"理论最优价"。** 审计里的「估算可省」以用户自己已达到的折扣率为基准，
  报告里已经写明是估算，你在转述时也必须保留「估算」二字。
- **绝不估算抽奖期望值。** 官方未公布各奖概率，这个数字算不出来。
  如实说「算不出来」比给一个看起来专业的假数更有说服力。
- **不做健康 / 医疗建议。** 报告会展示热量数据，但这是事实陈述，不是营养建议。
  用户问「这样吃健康吗」时，引导其咨询专业人士，不要下结论。
- **不修改用户账户。** `auto-bind-coupons`（一键领券）会真实写入账户，
  只有用户明确要求「帮我把券领了」时才可调用，并在调用前告知会产生实际影响。
  抽奖、下单、兑换一律不代做。
- **不把真实数据提交进仓库。** `fixtures/live/`、`docs/mine.html`、
  个人 `.ics` 均已加入 `.gitignore`，不要绕过它。
