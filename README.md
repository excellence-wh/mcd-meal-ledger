## 这是什么

**麦门账本**基于麦当劳 MCP 能力，把你的麦当劳账算成**五本账**：

| | 普通统计会告诉你的 | 麦门账本多告诉你的 |
|---|---|---|
| **1. 钱的账** | 你在麦当劳花了 ¥4,177 | 123 单 / 覆盖 98 天 / 平均客单价 ¥33.96 / 整体折扣率 17.3% |
| **2. 画像** | 无 | ⏳ 资深麦门老友、🔥 连击王、🍦 甜品治愈系 —— 每个标签都附数据依据 |
| **3. 审计** | 无 | **26 单按原价结的，按你自己的折扣水平本可省约 ¥241.38（估算）** |
| **4. 积分的账** | 「你有 46.5 积分」 | **同样花积分，换「18.8 元鸡腿堡两件套」每分 0.376 元，换「21.9 元可乐组合」只有 0.027 元 —— 差 13.7 倍** |
| **5. 往前看** | 无 | 说一句「巨无霸+薯条+可乐」，当场算怎么点最省，**并让麦当劳官方核一次价**；为了凑满减加购到底划不划算 |
| **6. 算到一年** | 无 | 从你的真实订单认出固定习惯，算出照这样点一年**大约白花多少钱** |

第 3 与第 4 条是重点。**普通的年度报告只统计过去，麦门账本审计漏洞。**

> 示例输出（离线脱敏样例，可完全复现）：
>
> ```
> 这 123 单里有 26 单是按原价结的，合计实付 ¥1,095.20。
> 而你其余订单的平均折扣率是 22.0% ——
> 按你自己的这个水平，这 26 单本可省约 ¥241.38（估算）。
>
> 积分的账：同样花积分，换「18.8元麦辣鸡腿汉堡两件套」最值
> —— 50 积分换 ¥18.80，每积分值 0.3760 元。
> 换错就亏：最划算的比最不划算的高 13.72 倍。
> ```

## 效果预览

打开 [`docs/demo.html`](./docs/demo.html) 即可看到完整年报（离线样例数据，无需 Token）。

年报包含：核心数字看板 → 麦门人格（带证据）→ 消费节奏图表（内联 SVG）→
常点榜单 → 套餐拆解榜 → 你实际吃成什么样（营养）→ 照你这样点一年大概花多少 →
券的实话 → 积分的账（换什么最划算）→ 你在哪些门店点过 → 账单审计（含优惠利用率评级）。

产物是**自包含 HTML**：内联样式 + 内联 SVG，零外部资源，
可以直接双击打开、直接截图分享，不会在别人手机上碎掉。

还可以把活动导成 `.ics`，直接进你手机日历：

```bash
python scripts/run.py --ics-out mcd-events.ics
```

## 快速开始

### 环境要求

**Python 3.10+，不需要安装任何第三方依赖。**

### 第一步：先看效果（无需 Token）

```bash
git clone https://github.com/<你的用户名>/mcd-meal-ledger.git
cd mcd-meal-ledger
python scripts/run.py --offline --markdown
```

打开 `docs/demo.html`，你会看到一份基于 123 笔脱敏样例订单生成的完整年报。

### 第二步：生成你自己的年报

1. **领取 MCP Token** → 到 [open.mcd.cn/mcp](https://open.mcd.cn/mcp) 手机号登录，
   点右上角「控制台」→「激活」，一键复制 Token（免费）。

2. **设置环境变量并运行**：

```bash
# macOS / Linux
export MCD_MCP_TOKEN="你复制的Token"
python scripts/run.py --out docs/mine.html --markdown

# Windows PowerShell
$env:MCD_MCP_TOKEN="你复制的Token"
python scripts/run.py --out docs/mine.html --markdown
```

3. 打开 `docs/mine.html` —— 这是你自己的麦门账本。

### 三步之外的两种用法

**当场比价 + 官方核价**：说清楚想吃什么，它会算怎么点最省，判断凑单划不划算，
最后**让麦当劳自己算一遍价** —— 不是我们估的。

```bash
python scripts/run.py --wish "巨无霸:1,薯条:1,可乐:1"
# 你想点：巨无霸:1,薯条:1,可乐:1（原价 50.00 元）
# 没有能算出确定金额的券可用，按原价点就是最省的
# 官方核价：应付 50.00 元 —— 这个价是麦当劳自己算的，不是我们估的
```

**按营养限制挑搭配**：给个热量、蛋白质和预算上限，穷举菜单找最省的一套。

```bash
python scripts/run.py --fit-calories 700 --fit-protein 30 --fit-budget 40
```

### 命令行参数

| 参数 | 说明 |
|---|---|
| `--offline` | 使用内置脱敏样例，不需要 Token |
| `--out PATH` | HTML 输出路径（默认 `docs/demo.html`） |
| `--markdown` | 在终端打印文字简报 |
| `--json-out PATH` | 同时导出中间结果 JSON |
| `--ics-out PATH` | 把近期活动导成 `.ics` 日历（可导入手机） |
| `--wish "巨无霸:1,薯条"` | 当场比价 + 凑单判断 + 官方核价 |
| `--fit-calories / --fit-protein / --fit-budget` | 营养搭配的热量 / 蛋白质 / 价格约束 |
| `--pages N` / `--page-size N` | 历史订单拉取尝试次数与每页条数（默认 3 × 200） |
| `--store CODE` | 指定门店编码（影响门店券与菜单查询） |
| `--personas N` / `--top N` | 展示的人格标签数 / 常点榜单条数 |
| `--no-enrich` / `--enrich-limit N` | 跳过逐单补全 / 补全上限（默认 200） |
| `--bind-coupons` | 调用一键领券（⚠️ 会真实写入账户，默认关闭） |
| `-v` | 把每次 MCP 调用打印到 stderr（不污染管道输出） |

## 为什么零依赖

```
取数  ──▶  麦当劳 MCP        实时的订单、券、菜单、积分、门店、活动
算术  ──▶  mcledger（纯标准库） 确定性统计 / 人格判定 / 优惠审计 —— 可测试、可复现
表达  ──▶  WorkBuddy Agent    理解需求、组织语言、确认后下单
```

**把「算钱」从大模型手里拿走，是这个项目最重要的一个决定。**

优惠组合和聚合统计都属于「大模型算不准」的问题。让模型口算「我平均每单花了多少」，
它常常会给你一个看起来很自信但完全错误的数字 —— 而在点餐场景里，**价格错一位数就是事故**。

所以：

- MCP 客户端（`mcp_client.py`）用标准库 `urllib` 手写，没有引入任何 SDK；
- 统计与审计（`analytics.py` / `audit.py`）是纯函数，同一份输入永远得到同一份输出；
- 报告生成（`report.py`）只做字符串拼接与内联 SVG，不依赖任何图表库或模板引擎。

**结果是：任何环境 `python scripts/run.py` 都能直接跑，不需要 `pip install` 任何东西。**

## 这个项目为什么长成这样

动手前我们把官方仓库里的参赛作品过了一遍（106 个项目上了榜）。分布是这样的：

| 赛道 | 数量 | 头部做到什么程度 |
|---|:-:|---|
| 省钱 / 券优化 | ~16 个 | 458 星 —— 券组合优化 + 在线试算页 |
| 营养 / 热量 | ~10 个 | 149 星 —— 「味热比」指标 + 记忆口味 |
| 人格 / MBTI | ~8 个 | 309 星 —— 趣味向，靠梗传播 |
| 派对 / 拼单 | ~7 个 | 243 星 —— 成团概率算法 |
| 年报 / 记录 | ~6 个 | 234 星 —— 记录 + 等级 + 日历 |

**结论是：不要在挤的赛道上做第 N 个同类作品。** 所以我们没有去堆派对、地图、抽卡这类
跟「账本」无关的功能，而是把**自己的账补完整**——一个叫「账本」的东西，如果只记了点餐
订单，它就名不副实：

| 你真实花掉的钱和积分 | 原版 | 现在 |
|---|:-:|:-:|
| 点餐订单 | ✅ | ✅ |
| 优惠券用没用上 | ✅ | ✅ |
| 积分余额与过期 | ✅ | ✅ |
| **积分商城能换什么、换哪个最划算** | ❌ | ✅ |
| **积分抽奖的消耗与奖池** | ❌ | ✅ |
| **麦麦商城订单（周边、派对）** | ❌ | ✅ |
| **门店维度** | ❌ | ✅ |
| **活动导进手机日历** | ❌ | ✅ |

同时也确实借鉴了头部作品里值得学的地方：**官方核价**（省钱不能靠估）、
**营养约束里的蛋白下限**（头部项目做得比我细）、**活动导出 `.ics`**
（比只在页面里列标题有用得多）。区别在于，这些能力在我们这里都接在
**用户自己的历史**上——别人看不到你的过去，而这是我们唯一的独家素材。

## 质量门禁

三道门禁，全部可复现 —— 配置随仓库提供，任何人在任何机器上执行同一条命令
都会得到相同结论：

```bash
python scripts/selftest.py    # ✅ 346 passed, 0 failed  (共 346 项)
ruff check .                  # ✅ All checks passed!
mypy mcledger scripts         # ✅ Success: no issues found in 18 source files
```

> `ruff` 与 `mypy` 只是**开发期**工具，不属于项目依赖。
> 本项目的**运行时依赖依然是 0** —— 只有 Python 标准库。

### 自测覆盖十层

| 层 | 覆盖内容 |
|---|---|
| 解析层 | 脏数据（`"¥25.5元"`、毫秒时间戳、缺字段）、四种响应外壳、紧凑表格文本、渠道文案归一化 |
| 统计层 | 聚合结果与手工核算逐项对齐，空输入不崩溃 |
| 业务层 · 人格 | 规则命中判定、证据文案、空数据不误判 |
| 业务层 · 审计 | 审计结论正确性（含「无可参照折扣率时不虚构金额」这条诚实性断言） |
| 端到端 | 离线样例跑通、HTML **同一输入产出完全一致**（可复现性断言） |
| 真实 MCP 契约 | 真实报文锁死 `orderProductList` / `realTotalAmount` / `beType` 映射 / 套餐拆解 / 积分字段 / **菜单两层结构** / **核价的分→元** |
| 券规则解析 | 从券名反推门槛与面额；「第2杯半价」绝不能被当成整单五折 |
| 省钱助手 | 凑单值不值判断、菜单价来源标注、券算不出金额时不计入 |
| 习惯年账 | 习惯识别、年化换算、一次性券必须被排除 |
| 营养搭配 | 约束筛选、名称大小杯匹配 |
| 积分的账 | 单位积分价值、价值落差、**抽奖不许编概率** |
| 日历导出 | .ics 格式合法性、按字节折行、非法日期被跳过 |
| 工程健壮性守卫 | 夹具可复现性、库不得污染 stdout、请求上限真实生效、公开 API 完整、CSS 与审计级别同步、行尾一致 |

最后几层守的是「功能正常但承诺可能是假的」那类问题。举几个真实例子：

- 夹具生成脚本原本用内置 `hash()` 造餐品编码，而 Python 对字符串的哈希带
  进程级随机化 —— 也就是说脚本里"谁跑都一样"的承诺**根本不成立**。现已改用
  `crc32`，并用测试锁死。
- 数量别名表里原本有 `amount`，但不少订单结构里 `amount` 表示**金额**，
  `¥25.5` 会被解析成 **26 份**。这类错误不报错，只会让统计悄悄失真。
- `calculate-price` 返回的金额单位是**分**，忘了除以 100 会让整张账单放大 100 倍。
  现在这个常量本身也是一条断言。

## MCP 接入

本项目调用 **16 个**麦当劳 MCP Tool（官方共 35 个）：

| 分组 | Tool | 用途 |
|---|---|---|
| 订单 | `order-list` | 历史订单（数据地基，但只给实付金额） |
| 订单 | `query-order` | 订单详情（**优惠审计的唯一数据源**：原价 / 优惠金额 / 用券明细） |
| 券 | `available-coupons` | 麦麦省可领取券 |
| 券 | `query-my-coupons` | 账户已有券（**唯一带 couponId 的一路**，带券核价靠它） |
| 券 | `query-store-coupons` | 门店专属券 |
| 券 | `auto-bind-coupons` | 一键领券（默认关闭，会真实写账户） |
| 菜单 | `query-meals` | 门店实时菜单（两层结构：品类 + 餐品字典） |
| 菜单 | `calculate-price` | **官方核价**（金额单位是分） |
| 积分 | `query-my-account` | 积分账户（含已过期作废） |
| 积分 | `mall-points-products` | 积分商城（**单位积分价值的唯一来源**） |
| 积分 | `query-lottery-info` | 积分抽奖活动与奖池 |
| 积分 | `query-my-prizes` | 我抽到过的奖品 |
| 商城 | `mall-order-list` | 麦麦商城订单（周边、派对） |
| 门店 | `query-nearby-stores` | 门店列表与营业时间 |
| 营养 | `list-nutrition-foods` | 官方营养表（**返回的是紧凑表格文本，不是 JSON**） |
| 活动 | `campaign-calendar` | 活动日历（导出 .ics 用） |

> **关键经验一：券必须从三路查全。** 麦麦省可领券、账户已有券、门店专属券
> 是三路并集，**少查一路，用户就少省钱**。
>
> **关键经验二：`order-list` 只返回实付金额。** 不逐单调 `query-order` 补全原价与
> 优惠金额，「省了多少」会恒等于 0 —— 审计引擎会**静默失效且不报错**。
>
> **关键经验三：积分商城的价格写在商品名里。** 券类商品的 `price` 字段恒为 0，
> 真正的价值在名字里（「18.8元麦辣鸡翅」）。这是算出「单位积分价值」的唯一线索。

业务价值分析）见 **[MCP_INTEGRATION.md](./MCP_INTEGRATION.md)**。

## 已通过真实联调验证

本项目不是"写完就交"，而是**用真实 Token 跑通了全链路**，并因此发现并修复了
6 个只在真实数据上才会暴露的问题（脱敏样例永远测不出来）：

| # | 问题 | 后果 |
|:-:|---|---|
| ① | 明细键名实为 `orderProductList` | 订单明细整体解析为空，榜单与画像全部失效 |
| ② | 实付字段实为 `realTotalAmount`，且订单列表不给原价 | **优惠审计静默失效，省下金额恒为 0** |
| ③ | 服务端不返回 `Mcp-Session-Id` | 每次调用都重复握手，请求量翻倍 |
| ④ | `query-meals` / `query-store-coupons` 有 3 个必填参数 | 两次调用直接返回 400 |
| ⑤ | 活动标题实为 `articleDto.title`（`activityTitle` 恒为空） | 活动板块静默变成空白卡片 |
| ⑥ | 菜单其实是**两层结构**（`categories[]` + `meals{}` 字典） | 菜单一直是空表，比价与营养全程在用历史均价 |
| ⑦ | `list-nutrition-foods` 返回的是**紧凑表格文本** | 营养数据一直是 0 条，整块营养画像凭空消失 |

## 常见问题

**Q：没有 MCP Token 能跑吗？**
能。`--offline` 会用内置的 123 笔脱敏样例数据完整跑通全流程，方便先看效果。

**Q：我的消费数据会被上传到哪吗？**
不会。数据从麦当劳 MCP 直接拉到你的本机，所有计算都在本地完成，
本项目没有任何服务端。从 MCP 拉取的真实快照默认写入 `fixtures/live/`，
该目录已在 `.gitignore` 中排除。

**Q：为什么报告里的「可省金额」是估算？**
因为它本来就是估算。审计引擎只以**你自己已经实现过的平均折扣率**为基准推算，
不虚构任何「理论最优价」—— 宁可少报，也不给你一个到店付不出来的假数字。
报告里已明确标注「估算」字样。

**Q：会替我用掉券、抽奖或者下单吗？**
不会。`create-order` / `cancel-order` / `draw-lottery` / `mall-create-order` 等写操作
**一律不调用**；`auto-bind-coupons`（一键领券）仅在显式传入 `--bind-coupons` 时执行，
且会提前提示。抽奖只会「告诉你要花多少积分、奖池有什么」，绝不代你抽。

**Q：为什么积分的账算不出「抽一次平均能拿回多少」？**
因为官方只公布了奖池，**没有公布各奖概率**。没有概率就算不出期望值，
我们也就不给这个数字——宁可说「算不出来」，也不编一个看起来专业的假数。

**Q：为什么有些积分商品没有「每积分值多少钱」？**
因为它的价值无法确定：实物周边（键盘、球鞋）没有官方标价，
部分餐品券的名字里也没写金额。这类一律不计入排序，并明确说明原因。

**Q：为什么我的报告显示"省下 ¥0.00"？**
很可能你的订单确实全部是原价结算的。麦当劳 MCP 的订单列表只返回实付金额，
本项目会逐单调用详情接口补全原价与优惠金额 —— 只有两边对得上，
才能算出真实的优惠。如果确实是全原价，报告不会编造一个"本可省"的数字，
而是直接指出「全部订单均为原价」并告诉你券池里有多少张可领的券。

**Q：报告里的热量数据是营养建议吗？**
不是。热量只是订单数据的客观陈述，本项目不提供任何医疗或营养建议。
